# Persistence

## Schema management: Flyway only ([ADR 0005](adr/0005-flyway-schema-management-and-postgres-portability.md))

- Migrations live in `src/main/resources/db/migration/` and are the **only** schema definition. There is no `schema.sql`, and `spring.sql.init.mode=never`.
- Hibernate runs with `ddl-auto: validate` in every environment, including tests. It checks that the entities match the migrated schema and refuses to start if they don't. `create`, `create-drop` and `update` are never used.
- To change the schema, add the next versioned migration (for example, `V4__...sql`). Never edit an applied migration.
- `SchemaMigrationTest` checks that V1–V3 were applied, that the named constraints and index exist, that `normalized_url` is `VARCHAR(2049) NOT NULL`, that the lifecycle columns have the expected shape and defaults, and that the database itself rejects duplicate codes and hashes and inconsistent lifecycle states.
- `V3MigrationTest` upgrades a separate database holding V2-era data (a mapping and a click) to the latest schema, and checks that nothing is lost and the mapping becomes `ACTIVE`.
- V3 (`V3__add_url_deactivation.sql`, [ADR 0009](adr/0009-url-lifecycle-deactivation.md)):
  - Adds `status VARCHAR(32) DEFAULT 'ACTIVE' NOT NULL` and a nullable `deactivated_at`, so existing rows become ACTIVE with no rewrite or deletion.
  - Adds the CHECK `ck_url_mapping_lifecycle`, which allows only `ACTIVE` with a NULL time or `DEACTIVATED` with a time. A new lifecycle state needs a migration that replaces it.
- V2 widens `normalized_url` from 2048 to 2049. Submitted URLs are capped at 2048, and normalization can add exactly one character (N5 turns an empty path into `/`), so `https://example.com?q=…` at 2048 characters normalizes to 2049. `destination_url` stays 2048, because it is the trimmed input.

## Domain ↔ table mapping

| Entity | Table | Notes |
|---|---|---|
| `UrlMapping` | `url_mapping` | Identity is immutable after insert (`updatable = false`, no setters). `destinationUrl` is the redirect target and `normalizedUrl` is the identity. `normalizedUrlHash` backs the uniqueness guarantee. `status` (`@Enumerated(STRING)`, never ordinals) and `deactivatedAt` are the only updatable columns, changed only through `deactivate()` |
| `ClickEvent` | `click_event` | Insert-only. `urlMappingId` is a plain column plus a DB foreign key, not `@ManyToOne` |

- Timestamps are `Instant` ↔ `TIMESTAMP WITH TIME ZONE`, stored in UTC and truncated to microseconds in code so a re-read equals the written value.
- Ids use `GENERATED BY DEFAULT AS IDENTITY`.

## Constraints and indexes (why each exists)

| Object | Purpose |
|---|---|
| `uk_url_mapping_short_code` | BR-2: one code ↔ one URL. Also serves the redirect lookup |
| `uk_url_mapping_normalized_url_hash` | BR-3: one normalized URL ↔ one mapping. On a 64-char hash, not the URL itself, because a unique btree on a 2048-char column can exceed PostgreSQL's ~2.7 KB index row limit |
| `fk_click_event_url_mapping` | A click must belong to an existing mapping. If future deletion must preserve click history, this favors a soft-delete lifecycle rather than physical deletion. |
| `ck_url_mapping_lifecycle` | Only known statuses, and `deactivated_at` is set exactly when `DEACTIVATED`. Backs the entity's invariant inside the database |
| `ix_click_event_mapping_clicked_at` | Serves `COUNT(*)`/`MAX(clicked_at)` per mapping, and future time-range analytics |

## Transactions

| Operation | Boundary |
|---|---|
| `UrlService.shorten` | **None around the loop.** Each `saveAndFlush` is its own transaction, so a unique violation affects only that attempt |
| `UrlService.resolve` / `resolveForRedirect` | `@Transactional(readOnly = true)`. Commits and closes before analytics runs. `resolve` ignores the lifecycle (analytics); `resolveForRedirect` refuses mappings that can't redirect |
| `UrlLifecycleService.deactivate` | `@Transactional`. `SELECT … FOR UPDATE` on the one row, the entity transition, and an UPDATE at commit. Concurrent deactivations of a row are serialized; plain reads don't request the lock |
| `AnalyticsService.recordClick` | `TransactionTemplate` with `REQUIRES_NEW`; the catch sits outside it (ADR 0006) |
| `AnalyticsService.analyticsFor` | Resolve, then one aggregate query |

`spring.jpa.open-in-view=false`, so no session spans the web request.

## H2 is not PostgreSQL

H2 runs with `MODE=PostgreSQL;DATABASE_TO_LOWER=TRUE`, and the migration uses only SQL that both databases accept. That catches obvious dialect drift. It does **not** make H2 behave like PostgreSQL:

| Area | Difference | How the design copes |
|---|---|---|
| Transaction abort | PostgreSQL aborts the whole transaction after any failed statement; H2 does not | Every insert attempt runs in its own transaction; nothing is retried inside a failed one |
| Error reporting | SQLSTATE codes and messages differ | Code relies only on Spring's `DataIntegrityViolationException` translation, never on vendor codes or messages |
| MVCC and locking | Different implementations and isolation defaults | Inserts rely on unique constraints, which both enforce atomically. The one lock, deactivation's `SELECT … FOR UPDATE` on an existing row, is supported by both; `DeactivationConcurrencyTest` verifies it on H2 only |
| Identity allocation | Different sequence caching and gaps | Ids are never assumed contiguous or meaningful |
| `CHAR` padding | Semantics differ | `VARCHAR` used throughout |
| Durability | In-memory: all data is lost on restart | Acceptable for the prototype only |

**Concurrency tests on H2 do not prove PostgreSQL behavior.** Before relying on PostgreSQL:
1. Add the PostgreSQL driver and a `postgres` profile (datasource via environment variables).
2. Run the same Flyway migrations.
3. Add Testcontainers-based integration and concurrency tests against real PostgreSQL.

These steps are future work and are not part of this prototype.

Operational note: Flyway 12.4 logs a WARN that H2 2.4.240 (managed by Spring Boot 4.1.1) is newer than its last verified H2 version. The migration is verified by `SchemaMigrationTest`. The version isn't overridden, so the build stays on Boot's managed versions.
