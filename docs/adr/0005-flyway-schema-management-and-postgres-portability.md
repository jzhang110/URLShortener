# ADR 0005: Flyway schema management and PostgreSQL portability

**Status:** Accepted

## Problem
The schema must be reproducible, versioned, and ready for the planned move to PostgreSQL. Two competing sources of truth, such as `schema.sql` plus Hibernate DDL, drift apart.

## Alternatives
1. Hibernate `ddl-auto=update/create`. It isn't versioned, isn't reviewable, and is unsafe for production.
2. `schema.sql` via Spring SQL init. It isn't versioned, so incremental changes are impossible.
3. Liquibase.
4. **Flyway with plain SQL migrations.**

## Decision
Option 4:
- Flyway is the single schema authority.
- `ddl-auto: validate` in every profile, so a mismatch between entities and schema fails startup (and therefore tests).
- `spring.sql.init.mode=never`.
- Migrations use the SQL subset shared by H2 and PostgreSQL: `GENERATED BY DEFAULT AS IDENTITY`, `VARCHAR`, `TIMESTAMP WITH TIME ZONE`, and named constraints.
- H2 runs in `MODE=PostgreSQL`.

Plain SQL was chosen over Liquibase's abstraction because the target database is known (PostgreSQL) and SQL is easier to review.

## Tradeoffs
- (+) One reviewable definition. The migrations deliberately use only SQL constructs shared by H2 and PostgreSQL, so they're designed to be portable. Drift between entities and schema is caught at startup by Hibernate validation. Running them on a real PostgreSQL database has **not** been verified in this prototype.
- (−) H2 compatibility mode is not PostgreSQL. The known differences are documented in [persistence.md](../persistence.md). Testcontainers or equivalent real-PostgreSQL integration tests are required before production use.
- (−) Adds the Flyway dependency. That's justified, because it's the standard, maintained tool for this job.
