# Persistence / database conventions

- **Flyway is the only schema authority** (ADR 0005). New change = new `V<n>__description.sql`. Never edit an applied migration.
- **Hibernate `ddl-auto: validate`** everywhere. `create`, `create-drop`, `update` and `schema.sql` are forbidden.
- **Portable SQL** that H2 (`MODE=PostgreSQL`) and PostgreSQL both accept:
  - `GENERATED BY DEFAULT AS IDENTITY`
  - `VARCHAR`, not `CHAR`
  - `TIMESTAMP WITH TIME ZONE`
  - explicitly named constraints and indexes (`uk_`, `fk_`, `ix_`, `ck_`)
- **Don't assume H2 behaves like PostgreSQL.** See [persistence.md](../persistence.md). Code must not depend on vendor error codes, isolation behavior or id contiguity.
- **Integrity lives in the database.** Uniqueness, foreign keys and NOT NULL are DB constraints. Application checks are only fast paths.
- **Index only for a known access pattern,** and document the query it serves.
- **Entities.**
  - JPA annotations match the migration (column names, nullability, lengths).
  - `protected` no-arg constructor for JPA.
  - No setters. Identity data is `updatable = false`; state that legitimately changes (the mapping lifecycle, ADR 0009) changes only through intent methods that keep invariants, backed by a CHECK constraint.
  - Enums are persisted with `EnumType.STRING`, never ordinals.
  - `Instant` for timestamps, truncated to microseconds.
- **Relationships across features** use id columns with FK constraints, not JPA associations, unless both entities belong to the same feature.
- **Entities** live in `<feature>/domain`, and **repositories** are Spring Data interfaces in `<feature>/repository`.
- **Queries** use derived methods or JPQL, and aggregate in the database (`COUNT`, `MAX`), not in Java.
- **Transactions** are short and declared on services. Each retryable insert gets its own transaction (ADR 0004), and so does each failure-tolerant side effect (ADR 0006).
- **Mappings are never physically deleted,** because click events reference them. Lifecycle changes go through `url_mapping.status` (ADR 0009); a future soft delete is a new status value.
- **Locks only for read-modify-write on an existing row.** Inserts rely on unique constraints (ADR 0004). A lifecycle change locks its one row (`PESSIMISTIC_WRITE`) inside a short transaction (ADR 0009).
